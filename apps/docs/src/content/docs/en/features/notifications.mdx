When something happens in the system (an approval reaches you, a notice is published, an export is ready), it lands in the bell in the top bar first; then, depending on the admin's and your own settings, it can also go out by email or SMS, or to a Feishu, DingTalk or WeCom group. Admins can also publish notices with attachments and a chosen audience.

This page first shows how to get a notification into an inbox and the order in which the system decides whether to send it, then covers notices, group bots and common problems.

## UI entry points

| Screen | Path | Permission code | What it does |
|---|---|---|---|
| Bell in the top bar · **Message center** | `/notification` | Any signed-in user | Your own in-app messages, unread count, mark all as read |
| Dashboard "Notices" card · pop-up after sign-in · top banner | — | Any signed-in user | Notices from the reader's side; who sees what is [below](#notice-content-and-visibility) |
| **System → Notices** | `/plugins/notice` | `sys:notice:add` to open; `edit` · `del` · `export` | Publish, edit and delete notices, read statistics |
| **Notifications → Notification policy** | `/notify/policy` | `sys:notification:policy:list` · `edit` | System policy per notification type × channel |
| **Notifications → Delivery records** | `/notify/delivery` | `sys:notification:delivery:list` · `resend` | The result of every external send; failed ones can be resent |
| Group bots | `/notify/bot` | `sys:notification:bot:list` · `add` · `edit` · `del` · `test` | Feishu / DingTalk / WeCom bot URLs and signing secrets |
| **SMS → SMS configurations / SMS logs** | `/sms/config` · `/sms/log` | `sms:config:list` · `add` · `edit` · `del` · `test`; `sms:log:list` · `del` | SMS provider credentials and templates, the result of every SMS |
| **Profile → Notifications** | `/profile` | The user | Whether each notification type also goes by email / SMS; cells the system policy forces are locked |

There is also `POST /api/v1/sys/notifications` (`sys:notification:send`) for admins to send an in-app notification by hand.

## Quick start

In-app messages work out of the box. Below, approval reminders are wired to email; about ten minutes:

1. Under **System → Config → Email service**, fill in the SMTP server, account and password. For QQ Mail, 163 and similar this is the "authorization code" generated in the mailbox settings, not the login password.
2. Set `NOTIFICATION_WEB_BASE_URL` in `.env` to your real address and restart the backend, or the "go to it" link in emails points at `localhost`.
3. Have the approver bind an email under **Profile** (enter it → receive a code → bind; this step itself uses the SMTP settings from step 1). Email is on by default for approval reminders — you can see it under **Notifications → Notification policy**.
4. From another account start an approval request, open it under "My requests" and click remind.
5. Open **Notifications → Delivery records**: if the row says *Sent*, it worked. If it says *Skipped* or *Failed*, the reason column says why — see [Troubleshooting](#no-email-arrived).

## Processing order

Once a notification is created, this is how the system decides who gets it and on which channels:

<DiagramFlow {...flows.notify.en} />

- **In-app is always sent**; only email and SMS look at the policy. The policy has four modes: off, on by default, off by default, forced. Users can change "on / off by default" under **Profile → Notifications**; "forced" is locked.
- **"Off" leaves no row, "skipped" does**: channels switched off by policy or preference are not considered at all; channels that should have sent but couldn't (no email, unverified phone, disabled account) get a *Skipped* row you can find in delivery records.
- **Master switch**: turning off `NOTIFICATION_EXTERNAL_ENABLED` in System → Config leaves only in-app messages; anything already queued still goes out.

## Real-time inbox

Inbox rows live in `sys_notification` under four categories: system, announcement, task (background exports) and workflow. When a row is written, the server emits a Socket.IO `notification:new` event **with an empty payload**; the browser refetches the list and unread count over REST. Permission checks therefore happen only in the REST API, and the unread badge is fetched over REST on every page load — a notification that arrived while the socket was disconnected still shows up. If the unread-count request fails, the bell shows `!` instead of an empty badge, which would look the same as "nothing unread".

A broadcast is one row, not one per user; read state is kept per user in `sys_notification_read`. Broadcasts written before an account was created count as read for that account, so a new hire does not log in to dozens of old red dots — except notices that require acknowledgement.

Approvers are not sent inbox rows for new tasks; the Approval center's to-do badge updates through a separate `workflow:todo` socket event (see [Approval workflow](/en/features/approval-workflow/)).

## Notice content and visibility

A notice has a rich-text body (Tiptap editor), up to 20 attachments, and these switches:

| Setting | Effect |
|---|---|
| Type · level | notice or announcement · normal, important or urgent |
| Pinned | sorts first; pinned + urgent + unread notices also show as a banner (up to 3) |
| Expiry / schedule | hidden after `expire_time`; invisible until `publish_time`. The Celery task `notice.sync_inbox` runs every 60 s to publish scheduled notices and retract expired ones |
| Pop-up | shown in a dialog after sign-in until read (up to 10, with body) |
| Require acknowledgement | the reader must click "I've read this"; "Mark all read" skips these rows. Only allowed together with pop-up (otherwise 422) |
| Show on sign-in page | readable without signing in, rate-limited to 30 requests per minute per IP; returns at most 5 items with a 200-character plain-text summary |
| Audience | departments (including all sub-departments), roles (enabled ones) and users. No audience rows = everyone. Sign-in page + audience is rejected with 422 |

Visibility has one definition, `crud_notice.readable_clause(viewer)` in [`crud_notice.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/plugin/notice/crud/crud_notice.py): not deleted, shown, published, not expired, and the viewer is in the audience. The reader list, detail, pop-ups, banner and **attachment downloads** all use it, and the inbox reads the same audience table, so "it's in my bell" and "I can open it and download the file" cannot disagree. Hidden, expired, unpublished or out-of-audience notices all return 404 — a 403 would confirm the notice exists. Admins with `sys:notice:add` get read statistics: who in the audience has and has not read it.

Attachments are committed in the same transaction as the notice. Each must exist and not be in the recycle bin, must be readable by the person publishing (otherwise anyone with publish rights could expose someone else's private file), and must not be a public file.

:::caution
Images embedded in the rich-text body are public files (`/uploads/{key}`): an `<img>` tag cannot send an auth header. They stay reachable even when the notice is hidden or limited to an audience. Put confidential material in attachments.
:::

## Channel routing

Each plugin declares its notification kinds in a `notification_kinds.py`, which the notification plugin discovers at startup. This is the real declaration from [`plugin/workflow/notification_kinds.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/plugin/workflow/notification_kinds.py):

```python
register_notification_kind(
    'workflow.remind',
    label='审批催办',
    category=NotificationCategory.WORKFLOW,
    defaults={'inapp': 'forced', 'email': 'default_on', 'sms': 'default_off'},
    sms_template='workflow_remind',
    sms_params=lambda title, content: {'title': title[:_SMS_TITLE_MAX]},
)
```

For each recipient and external channel, the router in [`service/routing.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/plugin/notification/service/routing.py) combines three things: the admin **policy** (`off`, `default_on`, `default_off` or `forced`, editable under **Notifications → Notification policy**), the user's own **preference** (**Profile → Notifications**; forced cells are locked), and whether the user has an **address**. In-app is always `forced`. A kind that is not declared for a channel cannot be switched on for it. SMS requires a registered SMS template because mainland-China SMS can only send pre-approved templates, and it is only sent to a phone number the user verified themselves — an admin-entered number gets a `skipped / phone_unverified` row instead.

The built-in kinds and their defaults:

| Kind | In-app | Email | SMS | Group bot |
|---|---|---|---|---|
| `workflow.remind`, `workflow.timeout` | forced | on | off | — |
| `workflow.sent_back` | forced | on | — | — |
| `workflow.result` | forced | off | — | yes |
| `workflow.cc`, `workflow.withdrawn` | forced | off | — | — |
| `workflow.task_assigned` ("you have a new task") | no row | off | — | — |
| `announcement` (notices) | forced | — | — | yes |
| `open.webhook.disabled` | forced | on | — | yes |
| `system`, `export.done`, `export.failed` | forced | off | — | — |

Broadcast kinds (notices, the daily greeting) never go to email or SMS: one broadcast row would fan out into a company-wide mass mail.

Calling code uses one entry point, `create_in_tx(db, kind=..., user_ids=..., title=..., content=..., link=...)` in [`notification_service.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/plugin/notification/service/notification_service.py). It writes the inbox rows and delivery rows in your transaction, does not commit, and returns a `Dispatch` whose `after_commit()` pushes the socket event and wakes the worker.

## Delivery and retries

The Celery task `notification.deliver_pending` runs every 15 seconds and is also kicked right after each commit. A worker claims a row with `UPDATE … SET status = 'sending' WHERE id = ? AND status IN (…)` and sends only if exactly one row changed. Failed sends retry after 60, 300, 1800 and 7200 seconds (default `NOTIFICATION_RETRY_MAX = 4`). For SMS and group bots, a result that **may** have been delivered — the connection was made, then timed out — is recorded as `unknown` and **not** retried, because a retry would mean a duplicate. Email does retry on connection errors and timeouts: a duplicate email costs less than a missed reminder. Rows stuck in `sending` for more than 600 s become `unknown` rather than going back to `pending`.

**Notifications → Delivery records** lists every row with its status (`pending`, `sending`, `sent`, `failed`, `exhausted`, `skipped`, `unknown`) and reason, masks phone numbers and email addresses in the list, and can resend `failed`, `exhausted` or `unknown` rows. Records are kept 30 days by default.

## Group bot platforms

Feishu (including `open.larksuite.com`), DingTalk and WeCom, configured under **Notifications → Group bots**. A bot subscribes to kinds marked `bot=True` — currently notices, approval results and "webhook endpoint disabled". Kinds that address the reader as "you" (CC, new task, sent back) are deliberately not subscribable: everyone in the group would read "you". Notices with an audience are not posted to groups, since a bot posts to the whole group; if the audience is later widened to everyone, the notice is posted once.

- **One delivery row per notification per bot**, regardless of how many people received it.
- **URL allow-list**: the webhook must sit on the platform's official prefix (scheme, host, port and path compared separately; userinfo and `.` / `..` path segments rejected; redirects not followed). Private deployments add `NOTIFICATION_BOT_EXTRA_URL_PREFIXES`, which must be https in production.
- **Signing**: Feishu and DingTalk signatures are supported; WeCom has none, so the `key` in its URL is the credential.
- **Rate limits** are counted before sending: Feishu 100/min and 5/s, DingTalk and WeCom 20/min. Over the limit, the row moves to the next minute without using up a retry.
- **Plain text only**, never markdown: titles are user input, and markdown would let someone post a link that looks system-generated. WeCom text is truncated at 2048 bytes, not characters.
- A read timeout counts as `unknown` and is not retried — a duplicate in a group chat is more visible than a duplicate email.

Links in bot messages and emails are built from `NOTIFICATION_WEB_BASE_URL` (default `http://localhost:8888`); set it to your real address before deploying. The step-by-step setup for a Feishu bot is in the [group bot guide](https://github.com/yile2020/fastapi-react-admin/blob/main/docs/guides/notify-bot.md).

## Protecting webhook URLs

A webhook URL is a credential: whoever has it can post to the group. The URL and signing secret are encrypted with `NOTIFICATION_ENCRYPT_SECRET_KEY` (32 bytes as 64 hex characters; without it, saving a bot is refused rather than storing plaintext). The API only returns a masked `webhook_hint`, and `webhook_url` / `sign_secret` are redacted from the operation log.

The less obvious leak was httpx itself: at INFO level it logs `HTTP Request: POST <full URL>`. The first real Feishu test put the token into the access log. The first fix only covered the API process, but the Celery worker — which does the actual sending — configures logging separately. The fix now sits at module top level in [`common/log.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/common/log.py) (`logging.getLogger('httpx').setLevel(logging.WARNING)`) and is covered by two tests, one of which configures logging the way `celery -l info` does in a subprocess.

## Troubleshooting

### No email arrived

Open **Notifications → Delivery records**, find the row for the recipient and check its status:

| Status / reason | What to do |
|---|---|
| No row at all | The channel is off: check the email column for this kind under **Notification policy** (off / off by default), whether the user turned it off under **Profile → Notifications**, and the external-channel master switch in System → Config |
| Skipped · *No address (email / phone)* | The recipient has no email; once added, later notifications are sent (skipped rows can't be resent) |
| Failed · *Rejected by mail server* / *Channel misconfigured* | Check the SMTP account, authorization code, port and SSL match (port 465 needs SSL on) |
| Failed, will retry · *Network unreachable* | The backend cannot reach the mail server; it retries after 1 min, 5 min, 30 min and 2 h |
| Sent | The mail server accepted it — check the recipient's spam folder |

Rows stuck at *Pending* usually mean the Celery worker is not running: it does the sending.

### SMS not sent

Symptom: the delivery row says *Skipped · Phone not verified by its owner*.

Cause: numbers entered or imported by an admin never get SMS — one wrong digit and an approval title lands on a stranger's phone.

Fix: have the user bind their phone under **Profile** (receive a code, then bind); it then shows *Verified*.

### Saving a group bot fails

Symptom: `NOTIFICATION_ENCRYPT_SECRET_KEY is not configured, so group bot webhook URLs cannot be stored safely`

Fix: generate a key with `openssl rand -hex 32`, put it in `NOTIFICATION_ENCRYPT_SECRET_KEY` in `apps/api/backend/.env`, restart the backend and save again. A webhook URL is a credential for posting into the group, so it is never stored in plain text.

When the URL is malformed, the message names the right prefix — a Feishu URL must start with `https://open.feishu.cn/open-apis/bot/v2/hook/`. Copy the whole URL from the group settings, including the token at the end.

### Group misses a notice

Either the bot isn't subscribed to notices, or the notice **has an audience set**. A bot posts to the whole group and can't respect an audience, so restricted notices are not pushed; if the audience is later widened to everyone, it is pushed then.

### Someone can't see a notice

Invisible notices always answer "not found". The usual reasons: the scheduled publish time hasn't come, it has expired, the person is outside the audience (departments include sub-departments, roles count only when enabled), or the notice is hidden. Holders of `sys:notice:add` can see in the read statistics who in the audience has and hasn't read it.

### Resend is refused

Symptom: `Only failed or unknown deliveries can be resent (skipped ones lack an address; add it first)`

A skipped row was never actually sent. After adding the address, the next notification goes out normally; this one is not re-sent.

## Limitations

- Group bots subscribe by kind only; there is no per-workflow or per-department filter.
- Group delivery is written from the same entry point as person delivery, so a bot-subscribed event with no person recipient (for example, an admin terminating their own request) does not reach the group either. Exercise 2 of the [group bot guide](https://github.com/yile2020/fastapi-react-admin/blob/main/docs/guides/notify-bot.md) works through how to separate the two.
- The audience pickers on the notice form call the user, department and role list APIs; a notice editor without those permissions sees a "no permission" line instead of options.

## Settings

**Changed in the UI** (System → Config), no restart:

| Group | Key | Default | Notes |
|---|---|---|---|
| Notification delivery | `NOTIFICATION_EXTERNAL_ENABLED` | `true` | Master switch for external channels. Off = only in-app messages are written, no email or SMS goes out (anything already queued still goes) |
| Notification delivery | `NOTIFICATION_RETRY_MAX` | `4` | Retries after the first attempt; deliveries with an unknown outcome are not retried |
| Notification delivery | `NOTIFICATION_DELIVERY_RETENTION_DAYS` | `30` | Days to keep delivery records; removed by the nightly log cleanup |
| Email service | `EMAIL_HOST` · `EMAIL_PORT` · `EMAIL_SSL` | `smtp.qq.com` · `465` · `true` | Outgoing mail server |
| Email service | `EMAIL_USERNAME` · `EMAIL_PASSWORD` | — | Most providers want an app password here, not the login password; shown masked in the UI |

**`.env` only**, restart the backend after changing (they are in each plugin's `plugin.toml` `[settings]` and also declared as fields in `conf.py`, so container environment variables can override them):

| Key | Default | Notes |
|---|---|---|
| `NOTIFICATION_ENCRYPT_SECRET_KEY` | empty | Encrypts group-bot URLs and signing secrets at rest; empty = bots cannot be saved, nothing is stored in plain text |
| `NOTIFICATION_RETRY_BACKOFF_SECONDS` | `60,300,1800,7200` | Wait after each failure; past the end of the list the last value repeats |
| `NOTIFICATION_WEB_BASE_URL` | `http://localhost:8888` | Base for absolute links in emails; **set it to the real address before going live** |
| `NOTIFICATION_BOT_TIMEOUT_SECONDS` | `5` | Timeout when calling a bot |
| `NOTIFICATION_BOT_EXTRA_URL_PREFIXES` | empty | URL prefixes allowed besides the official ones (self-hosted Feishu / DingTalk / WeCom); https only in production |
| `SMS_ENCRYPT_SECRET_KEY` | empty | Encrypts SMS provider credentials at rest; empty = configurations with credentials cannot be saved |
| `SMS_GLOBAL_HOURLY_MAX` | `500` | Site-wide SMS cap per hour, against a buggy loop draining the balance; 0 = unlimited |
| `SMS_CAPTCHA_EXPIRE_SECONDS` · `SMS_CAPTCHA_MAX_ATTEMPTS` | `300` · `5` | Lifetime and allowed wrong attempts for SMS codes |
