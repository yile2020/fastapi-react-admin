**Config** lets admins change part of the system's settings from the UI — sign-in policy, password rules, session lengths, the mail server, uploads, log retention… Changes take effect immediately with no restart, and the backend refuses invalid values. The **data dictionary** is a "type → options" table (label, value, colour, order) that business pages use for dropdowns and status tags, maintained by operations staff themselves.

This page first walks through both — changing a password rule and creating a dictionary for a page — then the order in which a setting takes effect, then the groups, how pages read dictionaries, and common problems.

## UI entry points

| Screen | Path | Needed to open the page | Other permission codes |
|---|---|---|---|
| **System → Config** | `/plugins/config` | `sys:config:list` | View `sys:config:list` · **Add key** `sys:config:add` · delete `sys:config:del`; each row's **Change history** needs `log:change:list` |
| **System → Data dictionary** | `/plugins/dict` | `dict:type:list` | Types `dict:type:list` · `edit` · `del`; items `dict:data:list` · `add` · `edit` · `del` · `import` · `export` |

The query code opens the page; the other codes decide what can be changed.

## Quick start

**Change a password rule**, about two minutes:

1. Open **System → Config → Passwords & lockout**, set the minimum length to 200 and save: it's refused, with the allowed range (1–128).
2. Set it to 8 and save. No restart: under **Profile**, a 6-character new password is now refused with `Password must be at least 8 characters`.
3. Put the original value back.

**Create a dictionary for a page**, about three minutes:

1. Open **System → Dictionaries** and create the type "Customer level" with code `crm_level`.
2. Add three items: Key / `A` / danger, Regular / `B` / primary, Prospect / `C` / grey.
3. A page only needs the code — see [below](#reading-from-pages):

   ```tsx
   <DictSelect code="crm_level" value={level} onChange={setLevel} />
   <DictTag code="crm_level" value={row.level} />
   ```

## Effect order

A setting goes from saved to in effect in this order:

<DiagramFlow {...flows.config.en} />

- **While a group is on, database values override `.env`**: that's why turning the captcha off in `.env` does nothing — turn it off in Config, or switch the whole group off (see the [FAQ](/en/reference/faq/#captcha-required-despite-being-disabled)).
- **Secret values are encrypted**: secret-looking keys such as the mail password are stored encrypted with `CONFIG_ENCRYPT_SECRET_KEY`; the API never returns them, and the UI shows *Configured; leave blank to keep*.

## Effect timing and validation

- **No restart.** A write clears the cache, and the next read picks up the new value: sign-in and captcha settings are read on every request, email on every send, webhook and retention values straight from the database each time. Two groups only affect what comes after: **Sessions** apply to later sign-ins (existing sessions keep the rules they started with) and **File uploads** to uploads that start afterwards.
- **Each group has a master switch**, `<GROUP>_CONFIG_STATUS`. Set to `0`, the group is not read from the database and the `.env` values apply. Conversely, while the group is on, **database values override `.env`**, which is why turning the captcha off in `.env` does nothing (see the [FAQ](/en/reference/faq/#captcha-required-despite-being-disabled)).
- **The backend validates writes**, not just the input boxes: integers have bounds (minimum password length 1–128, session idle time 5 minutes to 90 days, for example), fixed-choice keys accept only their values, and two-factor cannot be made mandatory while `MFA_SECRET_KEY` is unset. It was tested once: without this check, calling the API directly with an admin token could set the minimum password length to 999, after which nobody could change their password.
- **Reads have a fallback too**: an invalid value in the database (emptied, out of range) falls back to the `.env` value for that item with an error logged, rather than making sign-in fail with a 500.

## Custom config keys

Yes, with **Add key**. Two things to know:

- Your own keys land in **Unmanaged keys**, with no description, unit or range check. The group drop-down only offers sign-in, passwords & lockout, email and AI.
- **The backend has no generic way to read them**: built-in items override `settings` because each one is mapped in code. Business code has to query the config table itself to use a key you added.

To add a runtime setting **like the built-in ones** (described, bounded, overriding `.env`), see the developer section below.

## Data dictionary

Two levels:

- **Dictionary type**: name, code (unique), remark.
- **Dictionary item**: its type's code, label, value, colour, sort order, status (normal / disabled), remark. Labels are unique within a type.

### Reading from pages

The frontend has three things in `_shared/dict.tsx`; you only pass the dictionary type code:

```tsx
import { DictSelect, DictTag, useDict } from '../_shared/dict'

<DictTag code="crm_level" value={row.level} />                    {/* in a table: value → coloured tag */}
<DictSelect code="crm_level" value={level} onChange={setLevel} />  {/* form dropdown, the value is a string */}
const level = useDict('crm_level')   // when you need the options yourself: level.options / level.labelOf(value)
```

They call `GET /api/v1/sys/dict-datas/options?codes=a&codes=b`:

- **Sign-in is enough, no dictionary-management permission needed.** An ordinary page's dropdown must be able to read the dictionary it uses; the dictionary **management** endpoints still require `dict:data:*`.
- Up to 20 codes per request, and every code gets a key: **a type with no options returns `[]`, not 404** (the old endpoint returns 404 for "no such type", "type is empty" and "all items disabled" alike, so the caller cannot tell them apart).
- Only enabled items, sorted by sort order **ascending**, the same order the dictionary page shows. If a type has items with the same value (only labels are unique in the database), the frontend keeps the one sorted first.
- The result is cached in Redis for 2 hours, and adding, editing, deleting or importing items and editing or deleting types clears it. Codes that match nothing are not cached, so a caller cannot fill Redis with made-up codes; codes missing from the cache are fetched in a single query, so one request hits the database at most once.

The old `GET /api/v1/sys/dict-datas/type-codes/{code}` is still there, but it needs the `dict:data:list` permission, returns 404 for an empty type and sorts **descending**; business pages should not use it. Items can be [imported and exported](/en/features/import-export/), matched to existing items by type code + label.

⚠️ **Use the dictionary for enums that operators maintain themselves** (customer level, ticket category, …). The built-in pages' menu type, sign-in status and data-rule operators are **tied to enums in the backend code**; changing the dictionary would not change the backend, so they are not wired to it and stay in the page.

⚠️ When loading fails, `DictTag` shows the raw value (dotted underline, click to retry) and `DictSelect` is disabled with "Failed to load · Retry" — never a blank. A value the dictionary does not have (item disabled or deleted, but still in old data) is shown as a grey tag with the raw value.

## Settings

Config and the dictionary have no further switches. `dict` is a **required plugin** (`PLUGIN_REQUIRED` in `.env`) and cannot be uninstalled.

## Adding a runtime setting

1. Seed data: add a row to each of the five init SQL files under `plugin/config/sql/`.
2. Write a data migration that inserts the row with `insert_if_absent`; running databases never re-run seed SQL, so without a migration only new installs get the key.
3. Declare the key in `core/conf.py` with a default, which is the fallback when the group is off or the value is invalid.
4. Add it to the group's `load_*` mapping ([`utils/dynamic_config.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/utils/dynamic_config.py)) and make sure that `load_*` is called on the code path that reads the setting; a new group also needs a `ConfigType`.
5. Add integers to `DYNAMIC_INT_BOUNDS` with the same `min` / `max` in the frontend's `pages/config/registry.ts`; `test_dynamic_config_bounds.py` checks the two agree. Fixed-choice keys go into `DYNAMIC_CHOICES`.
6. Add the description, unit and widget to `REGISTRY` in `registry.ts`; a new group also needs a nav entry, an icon and Chinese / English strings.

Rules and pitfalls are in [`pages/config/AGENTS.md`](https://github.com/yile2020/fastapi-react-admin/blob/main/packages/platform/src/pages/config/AGENTS.md).

## Troubleshooting

### Value out of range

Symptom: `USER_PASSWORD_MIN_LENGTH 必须在 1~128 之间，收到 200` (range messages are Chinese-only for now)

Fix: use a value in the stated range. The range lives in the backend; the input box flags it too, and direct API calls are refused the same way.

### Editing .env does nothing

Cause: the group is on in Config, so database values override `.env`.

Fix: change it in Config, or set the group's master switch (`<GROUP>_CONFIG_STATUS`) to `0` so the whole group uses `.env`.

### Session policy not applied

Session policy only affects **later** sign-ins; people already signed in keep the rules they signed in under. To apply new rules to everyone at once they have to sign in again (force them out under Online users, for example).

### Saving the mail password fails

Symptom: `No valid CONFIG_ENCRYPT_SECRET_KEY (16/24/32 bytes as hexadecimal), so config secrets cannot be encrypted`

Fix: generate a key with `openssl rand -hex 32`, put it in `CONFIG_ENCRYPT_SECRET_KEY` in `apps/api/backend/.env`, restart the backend and save again. Upgrading from 1.1.0? See [Upgrading](/en/reference/upgrade/).

### New item missing from dropdown

Check in order: the item is *active* (disabled items aren't returned); the page's code matches the dictionary type code; refresh the page (the frontend caches dictionaries for 5 minutes). Changes clear the backend cache, so there's no 2-hour wait.

### Grey raw values shown

That value isn't in the dictionary — its item was disabled or deleted while old data still carries it. Re-activate the item, or update that data.

## Limitations

- Secret values (keys ending in `PASSWORD`, `SECRET`, `TOKEN`, `API_KEY`…) can only be overwritten or cleared; the UI never shows the stored value, and data change history records only that they changed. Don't change `CONFIG_ENCRYPT_SECRET_KEY` once set — stored secrets could no longer be decrypted.
- Keys you add yourself have no validation and no generic accessor; the "visible to frontend" flag has no effect in the backend.
- The dictionary has no "built-in, read-only" flag: an admin can delete or change seeded items (such as "Normal" in "General status"). No built-in page depends on them, but once your own business page reads one, a deleted value shows as a grey raw value.
- A label is one piece of Chinese text in the database; the English UI translates it by that text through the language pack: translated if the pack has that exact text, not translated if an admin typed it.
- **No per-type control over who can read**: any signed-in user can read every dictionary's labels and values through the endpoint above (the dictionary **management** endpoints still require permissions). Don't put categories that only some people should see in the dictionary.
- The dictionary page lets you pick only 7 canonical colours (default, primary, success, info, warning, danger, grey). The Ant Design colour names used in the seed data (`green`, `processing`, `magenta`, …) are mapped to these by meaning on the frontend, without changing what is stored; when you edit such an item the dropdown shows "Current value: …", and leaving the colour alone saves it unchanged.
- Neither the Config page nor the dictionary page has a dedicated E2E test.
