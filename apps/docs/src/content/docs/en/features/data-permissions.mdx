Permissions come in two layers that don't replace each other: **function permissions** decide which pages, buttons and APIs a person can use; **data scopes** decide which rows those APIs return — two people can both open Users, and the department manager only sees their own department while head office sees everyone. Data scopes are applied automatically when the backend queries, so business code doesn't write a single check for them.

This page first walks through "own department only" with the seed data, then covers the order a request is judged in and how rules are written, and ends with common problems and what developers need to watch for.

## UI entry points

| Screen | Path | Permission code | What it does |
|---|---|---|---|
| **System → Data permissions** | `/system/data-permission` | Scopes: `data:scope:list` · `add` · `edit` · `del`, changing which rules a scope holds `data:scope:rule:edit`; rules: `data:rule:list` · `add` · `edit` · `del` | Data scopes on the left, the rules of the selected scope on the right |
| **System → Roles → Data scopes** | `/system/role` | View `sys:role:list`, change `sys:role:scope:edit` | Bind data scopes to a role; the role form also has an **Enable data-scope filtering** switch, and off means the role is not limited by data scopes (for a head-office role, say) |

Opening the Data permissions page requires `data:scope:list`.

## Quick start

Use the seeded "财务专员" (finance staff) role, which is bound to the "本部门数据权限" (own department) scope, and its user Wang Fang; about five minutes:

1. Sign in as an admin, open **System → Roles** and select "财务专员". The **Data scope** tab shows it is bound to "本部门数据权限", and **Enable data-scope filtering** is on in the role form.
2. In the **Permissions** tab, tick **System → Users** and its "query" button, then save. This is the function permission: without it Wang Fang can't open Users at all.
3. In a private window sign in as `wangfang` / `123456` and open **System → Users**: only people in "财务人事中心" (finance & HR) are listed.
4. Back in the admin window, change or unbind the scope under **System → Data permissions**; Wang Fang sees the change after refreshing the page — no new sign-in needed.

## Processing order

Every request is judged in this order. The first two steps decide whether the API may be called; the last three decide which rows come back:

<DiagramFlow {...flows.dataScope.en} />

- **Several roles: the widest wins.** If any enabled role has filtering turned off, no other role's limits are looked at. Adding a role adds abilities — and can remove limits.
- **A rule only affects tables that have its column.** "Department ID equals my department" becomes `dept_id = <yours>` on users; the department table has no `dept_id` column, so the rule does nothing there and the department list stays complete.
- **OR lifts AND.** All rules are flattened, then combined as "(all AND rules) or (any OR rule)". When one scope mixes both, the data permissions page shows a warning.

## RBAC vs data scope

| | RBAC (permission codes) | Data scope (row-level) |
|---|---|---|
| Question it answers | Can this user call `GET /sys/users`? | Which users does that call return? |
| Configured in | **System → Menus** (codes on button rows) + **System → Roles → Permissions** | **System → Data permissions** + **System → Roles → Data scope** |
| Enforced in | [`rbac.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/common/security/rbac.py) `rbac_verify`, per endpoint | [`data_scope.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/common/security/data_scope.py) `DataScopedCRUD`, per DAO |
| Denied looks like | HTTP 403 | Fewer rows (or a 404 on a detail endpoint) |

## RBAC checks

Menus live in `sys_menu` (type 0 directory, 1 page, 2 button). Button rows carry a comma-separated `perms` string; roles are granted menus. An endpoint declares the code it needs:

```python
@router.get(
    '/{pk}',
    summary='获取用户信息',
    dependencies=[Depends(RequestPermission('sys:user:list')), DependsRBAC],
)
```

`rbac_verify` then checks, in order: superusers pass; the user needs at least one enabled role with at least one menu; any method other than `GET`/`OPTIONS` also needs `is_staff`; finally the code must be in the `perms` of an enabled menu of an enabled role. A menu counts as enabled only if it **and every ancestor** are enabled, so disabling a directory disables the buttons under it.

The frontend reads the user's codes once from `/auth/codes`. [`<Can perm="…">`](https://github.com/yile2020/fastapi-react-admin/blob/main/packages/platform/src/auth/can.tsx) hides buttons and `requirePerm()` in a route's `beforeLoad` redirects to `/403`. Both are display only — the backend check is the boundary.

:::caution
A route that declares no permission code passes `rbac_verify` untouched (it returns early). Read endpoints need a code too: before issue #30, several `GET` endpoints (`/sys/users`, `/logs/opera`, …) only required a login, and an account bound to just the dashboard could read the full user list.
:::

## From rule to SQL

The chain is **role → data scope (`sys_data_scope`) → data rule (`sys_data_rule`) → one condition**. A scope is just a named bundle of rules; a rule has five fields. Here is one from the seed data:

| Field | Value | Meaning |
|---|---|---|
| model | `__ALL__` | every model that has the column (or a model name such as `Dept`, `User`) |
| column | `__dept_id__` | template for `dept_id`; `__created_by__` is the other column template |
| operator | `AND` | `AND` or `OR` — see the next section |
| expression | `==` | also `!=`, `>`, `>=`, `<`, `<=`, `in`, `not in` |
| value | `${dept_id}` | current user's department; `${user_id}` and `${now}` also exist |

On the `User` model this becomes `sys_user.dept_id = <current user's dept_id>`. `Dept` has no `dept_id` column, so the same rule leaves departments unfiltered.

[`filter_data_permission_for_user()`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/common/security/permission.py) evaluates it like this:

1. Superuser → no filter.
2. Any enabled role with **Enable data-scope filtering** switched off → no filter.
3. Collect the rules of every enabled scope of every enabled role into one set. Filtering on but no rules → the user sees **nothing**.
4. Compile each rule that applies to the queried model, then combine:

<details>
<summary>The combining code (developers)</summary>

```python
where_list = []
if where_and_list:
    where_list.append(and_(*where_and_list))
if where_or_list:
    where_list.append(or_(*where_or_list))
return or_(*where_list) if where_list else or_(1 == 1)
```

</details>

The final `or_(1 == 1)` only covers rules that are valid but target other models — a rule on `User` does not hide departments.

## Combining OR and AND

Because of the shape above: `or_(and_(all ANDs), or_(all ORs))`. With `parent_id == RA` (AND) and `status == 1` (OR), a user sees the union, not the intersection — the OR rule lifts the restriction. Rules are flattened across scopes *and* roles before this step, so two AND rules from two different roles also intersect. The Data permissions page shows a warning whenever one scope mixes AND and OR rules.

## Multiple roles

The widest role wins. One enabled role with filtering off makes every restrictive role irrelevant — granting a role adds capabilities *and* removes restrictions. Disabled roles and disabled scopes are ignored.

## Automatic filtering

No. The JWT middleware puts the authenticated user into a `ContextVar`, and the `DataScopedCRUD` base class appends the condition in `select()`, `select_model()` (fetch by primary key) and `count()`. Overriding only `select()` would miss detail endpoints: `GET /sys/depts/{pk}` for a department outside the scope now returns 404, not the row.

Every DAO must take a stance: inherit the default, or set `data_scope_enabled = False` with a reason. A test scans all `crud_*.py` files and fails on any class that still inherits `CRUDPlus` directly, and another checks the exemption list against the code. Scoped today: users, departments, roles, files, login and operation logs, scheduled tasks and their results. Exempt, with reasons in [`test_data_scope_coverage.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/app/admin/tests/security/test_data_scope_coverage.py): menus (the sidebar would go blank), dictionaries and settings (form dropdowns), the rule and scope tables themselves (an admin could lock themselves out), and notices (no ownership column to filter on).

## Background (Celery) tasks

Without a request there is no current user, and no current user means **no filter** — correct for cleanup jobs, CLI and startup code. Code that works *on behalf of a person* must say so:

```python
with scoped_to_user(user):
    async with async_db_session() as db:
        stmt = _restrict_ids(await spec.select(filters, user), spec, ids)
        ...
```

That is the export worker in [`export_service.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/app/admin/service/export_service.py): a large export queued by a department-limited user would otherwise read the whole table in the worker, without any error. `scoped_to_user(None)` raises `ValueError` on purpose. The [AI assistant](/en/features/ai-assistant/) runs every tool call through the same `scoped_to_user`. The opposite helper, `bypass_data_scope()`, is for system reads inside a request that are never shown to the user — login lookups and uniqueness checks.

## Misconfiguration safeguards

Two layers:

- **On save** ([`data_rule_service.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/app/admin/service/data_rule_service.py)): unknown model or column, an excluded column (`id`, `sort`, `deleted`, `deleted_time`, `created_time`, `updated_time`), a value that does not convert to the column type (`abc` for a bigint), or `__ALL__` with a plain column name → rejected with a message.
- **At runtime: fail closed.** If any rule cannot be interpreted, the whole filter becomes `false()` and the user sees nothing. A template that has no value — `${dept_id}` for a user without a department — makes that rule match nothing instead of putting the literal `'${dept_id}'` into SQL (on SQL Server that was a 500).

Earlier versions skipped rules they could not apply. The seed's own "本部门数据权限" (own department) scope was once `Dept.__dept_id__` — `sys_dept` has no `dept_id`, so it silently showed every department.

## Applying permission changes

No. The user's permission snapshot (Redis key `fba:user:<id>`) is cleared when roles, scopes or rules change, and the next request rebuilds it. Both the backend suite and the browser tests check this without a re-login.

## Troubleshooting

### Scope set, still sees everything

Check in this order:

1. Is the person a superuser? Superusers are never filtered.
2. Does **any** of their roles have **Enable data-scope filtering** off (an admin role left attached, for example)?
3. Does the rule land on this table? A rule for model `Dept` does nothing to the user list; with a column template like `__dept_id__`, the table must really have that column.
4. Is there an OR rule among them? It lifts all AND limits.

### No rows at all

Usual causes:

- The role has filtering on but no data scope bound — filtering with no rules means no rows.
- The user has no department and the rule uses `${dept_id}`: a rule whose value can't be resolved matches nothing.
- A rule can't be understood (its column was dropped, say): the whole filter closes to no rows, rather than opening up.

### Page shows access denied

Symptom: the page redirects to *Access denied*, or the API returns 403.

Cause: a missing function permission, unrelated to data scopes. Tick the page and its "query" button under **System → Roles → Permissions**.

If the API answers with one of these, the account itself is the problem:

| Message | Cause |
|---|---|
| `The role assigned to this account is disabled, please contact the administrator` | No enabled role (all disabled, or none assigned) |
| `No menu assigned to this account, please contact the administrator` | None of the roles has any menu ticked |
| `This account is not allowed to perform admin operations, please contact the administrator` | The user's admin-operations switch is off: reads work, creates, updates and deletes are refused |

### Saving a rule is refused

Rules are validated on save, and the message says what's wrong:

| Message | Fix |
|---|---|
| `The selected model has no such column` | Pick a column the table really has |
| `When the model is "all models", the column must be a template variable` | "All models" only takes column templates like `__dept_id__` / `__created_by__` |
| `This column is not allowed for data filtering` | `id`, `sort`, `deleted` and the created / updated times can't be used |
| `Value does not match the column type` | Text in a numeric column, for example; ID columns take a number or `${dept_id}` |

### When changes take effect

Immediately. Changing a role, scope or rule clears the affected users' permission cache on the backend; after a page refresh they get the new buttons and data. No new sign-in.

## Limitations

- Value templates are `${user_id}`, `${dept_id}` and `${now}` only. There is no "my department and all its sub-departments" template; the seed's "部门及以下数据权限" scope uses fixed rules on HQ's code and ID.
- `DataScopedCRUD` scopes reads. It does not rewrite `UPDATE` or `DELETE` statements, so a write path that changes rows by ID without reading them through a scoped DAO first is not covered.
- `exists()` is deliberately not scoped. It backs uniqueness checks; filtering it would let a user create a duplicate of a row they cannot see.
- When a parent department is filtered out, its visible children are shown at the top level of the tree.
- Superusers are never filtered. The open API (AK/SK-signed) reads the full data set on purpose; it is bounded by which endpoints each app is authorised for and by the fields its schemas expose.

## Settings

Data scopes themselves are configured in the UI. The keys below are for developers, set in `.env` / `conf.py`, and need a backend restart:

| Key | Default | Notes |
|---|---|---|
| `DATA_PERMISSION_MODEL_EXCLUDE` | `DataScope` · `DataRule` · two link tables | Models excluded from data filtering (not selectable in the rule editor) |
| `DATA_PERMISSION_COLUMN_EXCLUDE` | `id` · `sort` · `deleted` · `deleted_time` · `created_time` · `updated_time` | Columns that cannot be used in a rule |
| `DATA_PERMISSION_TEMPLATE_VARIABLES` | `${user_id}` · `${dept_id}` · `${now}` | Template variables allowed in rule values |
| `RBAC_ROLE_MENU_MODE` | `true` | `true` = permission-code mode (role → menus → permission codes); `false` = casbin mode, checking API path + method, in which features that rely on permission codes refuse every call |
