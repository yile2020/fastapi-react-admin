There are two ways to see whether the system is healthy. **The monitoring pages** are for people — the server's CPU, memory and disks, Redis memory and operations per second — and show only the present moment. **The health endpoint** `/api/health/status` is for external monitoring: no sign-in, and one call reports whether the API, database, Redis, scheduler and background worker are up — 200 when all are fine, 503 when any is not.

This page first runs a health check and deliberately stops a process to see how it's reported, then explains where the background heartbeats come from, then the two monitoring pages and common problems.

## UI entry points

| Screen | Path | Who |
|---|---|---|
| **Monitoring → Server** | `/monitor/server` | Superusers |
| **Monitoring → Redis** | `/monitor/redis` | Superusers |
| **Monitoring → Active sessions** | `/monitor/online` | Superusers; see [Session management](/en/features/login-sessions/) |
| Dashboard "Service status" card | `/dashboard` | Superusers |
| Health check | `/api/health/status` | No sign-in |

Monitoring pages and endpoints are guarded by **superuser**, with no permission codes: granting these menus to an ordinary role does not let it open them.

## Quick start

With everything running locally under `pnpm dev`, about five minutes:

1. Open `http://127.0.0.1:8088/api/health/status`: 200, with `api`, `database`, `redis`, `scheduler` and `worker` all `ok` under `services`, plus the version and commit at the end.
2. Stop the worker process in the `pnpm dev` terminal (or `docker stop` the worker container in production), wait three minutes and refresh: `worker` turns `stale` and the whole response becomes 503.
3. Start the worker again; it's back to 200 within a minute.
4. As a superuser open **Monitoring → Redis**, set refresh to 5 seconds and watch the ops/s trend grow.

For external monitoring (Uptime Kuma, a cloud monitor…), probe this URL and judge by status code — see [Deploying to a server](/en/getting-started/deployment/#external-monitoring).

## Heartbeats

The database and Redis are pinged on the spot; the scheduler and the worker have no port to probe, so they write heartbeats themselves:

<DiagramFlow {...flows.health.en} />

- **180 seconds before it's a failure**: three cycles by default, so a missed tick during a restart or deploy doesn't raise a false alarm.
- **Only components you operate**: broken mail, object storage, third-party sign-in or AI providers never make it 503 — check their own delivery records and call logs.
- **No details leak**: on failure only the exception's type name is given, never its message, so anonymous callers don't see connection strings.

## The two monitoring pages

**Server**:

- Four headline metrics: CPU, memory, the fullest disk, uptime; CPU and memory have trend lines
- CPU cores and frequency; memory total / used / free
- System: hostname, OS, architecture, IP, partition count
- Backend process: Python version, start time, CPU, resident memory, virtual memory, interpreter path
- Disk list (virtual file systems such as `overlay` and `tmpfs` are left out)

**Redis**:

- Used memory against the limit (`maxmemory`), fragmentation ratio (with an explanation)
- Key count, **for the current database only** (`DBSIZE`); other databases on the same Redis are not counted
- Operations per second and its trend
- Clients: connected, blocked, rejected (rejected is cumulative)
- Version, mode, role, port (as seen inside the container)
- Command stats: the 10 most-called commands, searchable

**Refresh**: manual, or every 5 / 10 / 30 / 60 seconds, 10 by default, kept in the URL (`?refresh=`). Polling stops while the tab is in the background and resumes when you come back.

Trend lines keep at most 40 points and vanish when the page closes. These pages answer "how is it right now"; they are not a monitoring system. For history and alerts, use a dedicated system such as Prometheus, Zabbix or your cloud's monitoring.

## Health check endpoint

`GET /api/health/status` needs no sign-in, is not rate-limited and is not recorded in the operation log. It checks five things concurrently:

| Item | How |
|---|---|
| `api` | Healthy if it responds |
| `database` | `SELECT 1`, 5-second timeout |
| `redis` | `PING`, 3-second timeout |
| `scheduler` | Beat's scheduling loop writes a heartbeat on every tick (at least one tick a minute, written at most every 15 seconds) |
| `worker` | Beat dispatches a `health.heartbeat` task every 60 seconds and the worker writes a heartbeat when it runs it |

A heartbeat older than 180 seconds is `stale`, one never written is `missing`, and the worker is `unknown` when Redis cannot be read or the scheduler itself is unhealthy (the worker heartbeat is dispatched by beat, so without beat there is nothing to judge by).

**All healthy returns 200; anything else returns 503**, with each item's status and heartbeat age in the body. Errors carry only the exception type name, never its message, so nothing like a connection string leaks to anonymous callers. When the backend is down entirely, nginx returns 503 with `{"status":"unavailable"}` and `Retry-After: 15`.

The body ends with `version` and `commit` (a 7-character commit hash), so you can tell which release is live; they never affect the 200 / 503 result, and `commit` is `null` when no commit was baked into the image. The frontend's own copy is in `/version.json`, and after signing in, **Help → About** in the top bar shows both side by side and flags a mismatch.

Which address external monitoring should probe, and why not `/healthz`, is in [Deployment](/en/getting-started/deployment/#external-monitoring). Container orchestration uses a separate `/health/ready` that checks only the database and Redis.

The dashboard's **Service status** card reads the same checks, plus how many sessions are online on web, desktop and mobile; it does not poll, and re-opening it within 20 seconds uses the cached result.

## Troubleshooting

### Health check stays 503

See which item isn't `ok`:

| Status | Meaning | Check first |
|---|---|---|
| `database` / `redis` is `error` | Can't connect | The database / Redis process and network; the `error` field holds the exception type |
| `scheduler` is `missing` or `stale` | Beat isn't running, or is stuck | Logs of the beat process / `fba_beat` container |
| `worker` is `stale` | The worker isn't running, or hasn't handled a heartbeat for 3 minutes | Worker logs; whether another project is stealing the queue (see [Scheduler](/en/features/scheduler/#job-didnt-run-on-time)) |
| `worker` is `unknown` | The scheduler itself is failing, so the worker can't be judged | Fix the scheduler first |

### Returns unavailable

Symptom: 503 with `{"status":"unavailable"}`.

Cause: nginx answered — the backend process can't be reached at all (not started, crashed, restarting). Check the api container's logs.

### Admins can't open monitoring

Server and Redis monitoring are superuser-only, with no permission code; granting the menus to a role doesn't open them.

### Redis key count looks low

The key count is **the current database only** (`DBSIZE`); keys in other databases on the same Redis aren't counted.

### Server page shows the container

It shows the machine or container running the backend API, not where the database or Redis run; inside a container, CPU and memory are what the container sees.

## Settings

All in `.env`; restart the backend after changing:

| Key | Default | Notes |
|---|---|---|
| `HEARTBEAT_MAX_AGE_SECONDS` | `180` | How old a heartbeat may get before it counts as unhealthy; three cycles by default, so missing one or two ticks (a restart, a deploy) does not alert |
| `SCHEDULER_HEARTBEAT_REDIS_KEY` · `WORKER_HEARTBEAT_REDIS_KEY` | `fba:health:scheduler_heartbeat` · `fba:health:worker_heartbeat` | Redis keys the heartbeats are written to |

The monitoring pages' refresh interval is chosen on the page and needs no configuration.

## Limitations

- Server monitoring describes **the machine (or container) running the backend API**, not the ones running the database or Redis. The IP is the local address used for an outgoing UDP connection, falling back to `127.0.0.1`.
- No history, no alerts.
- If beat is stuck while its loop keeps turning, the scheduler heartbeat may still be written and the health check won't notice.
- The two monitoring pages have no backend or E2E tests; the health check does.
