Giving a new colleague an account that shows the right menus and allows the right actions takes four screens: **departments** form a tree, a **user** belongs to one department and can hold several roles, a **role** ticks which menus and buttons it may use, and **menus** define both the sidebar and the permission code each button needs.

This page first builds a working account from scratch, then shows how a request can be stopped at the account, department and role levels, then the rules of each screen and common problems. Which rows someone sees (data scopes) is covered in [Data permissions](/en/features/data-permissions/).

## UI entry points

| Screen | Path | Needed to open the page | Other permission codes |
|---|---|---|---|
| **System → Users** | `/system/user` | `sys:user:list` | View `sys:user:list` · export `sys:user:export`. Create, edit, change permissions, reset password, reset two-factor and import are **superuser only** |
| **System → Roles** | `/system/role` | `sys:role:list` | View `sys:role:list` · edit and add / remove members `sys:role:edit` · change permissions `sys:role:menu:edit` · change data scopes `sys:role:scope:edit` · delete `sys:role:del` |
| **System → Departments** | `/system/dept` | `sys:dept:list` | View `sys:dept:list` · edit `edit` · delete `del` · import `sys:dept:import` · export `sys:dept:export` |
| **System → Menus** | `/system/menu` | `sys:menu:list` | View `sys:menu:list` · edit `edit` · delete `del` |

The "needed to open the page" column is the code the frontend route guard checks — each page's **query** code. A role with the menu ticked but not its query button is redirected to 403. Superusers skip route guards.

## Quick start

Give a new colleague an account that manages departments, about five minutes:

1. **System → Roles**: create a role "Department admin" with code `DEPT_ADMIN` (the code can't be changed later), and **turn off Enable data-scope filtering** — it's on by default, and a role with filtering on but no data scope sees no rows at all (see [Data permissions](/en/features/data-permissions/#no-rows-at-all)).
2. Select it, open **Permissions**, tick **System → Departments** and its query, create and edit buttons, and save. Query opens the page; the other buttons decide what can be done.
3. **System → Users**: create the user (superusers only) — pick the department, the "Department admin" role and an initial password that passes the password rules.
4. On that user's row open **Permissions & security** and turn **Admin sign-in** on. **New users have it off**; without it they can sign in and look, but every save is refused.
5. Sign in as the new account: the sidebar shows only Departments, and departments can be created and edited.

## Processing order

Each request checks the account in this order; only after all of them pass do data scopes apply:

<DiagramFlow {...flows.account.en} />

- **Disabling takes effect at once**: disabling a user ends all their sessions; disabling a department or role refuses its users on their next request, without waiting for a new sign-in.
- **Permission changes need a page refresh**: the backend applies them from the next request, but the menus and buttons cached in the browser don't change by themselves until the page is refreshed.
- **Page guards and APIs are separate gates**: the frontend decides which menus and buttons to show by permission code, and every API checks again on its own. A hidden button doesn't mean the API is unchecked, and vice versa.

## Superuser and admin sign-in

A user has two switches, changed under **Permissions & security** in the user list (superusers only, and not on yourself):

| Switch | What it does |
|---|---|
| **Superuser** (`is_superuser`) | Skips every permission-code and data-scope check; the sidebar shows every menu |
| **Admin sign-in** (`is_staff`) | Without it the account can sign in and read, but every write (any request other than GET) is refused with "This account is not allowed to perform admin operations" |

Superuser-only endpoints require **both**.

⚠️ **Users created by hand or by import start with Admin sign-in off**, so after their first sign-in they cannot save anything until a superuser turns it on. The switch's description in the UI says "With this off the account still exists but cannot get in"; in fact the account can still sign in and read, it just cannot change anything.

## User operations

- **Create**: a department is required, the password must pass the [password rules](/en/features/login-security/#password-rules), and the form requires at least one role. A user belongs to exactly one department and can have several roles; saving replaces the whole set of roles.
- **Disable / enable**: a user is either normal or disabled. Disabling **ends all of their sessions at once**, and their open pages go back to the sign-in screen.
- **Locked** is not a status: 5 wrong passwords in a row lock the account for 5 minutes (changeable in Config); it unlocks on its own, and there is no manual unlock in the UI.
- **Reset password**: superusers only, no old password needed; the new password still cannot repeat recent ones; all of the user's sessions end.
- **Delete**: several can be selected and deleted together, one by one, with failures reported. Superuser rows cannot be selected. Deletion is **logical** (the row stays in the database), but there is no restore in the UI.
- **Phone numbers** are unique; when an admin changes someone's number, its "verified" flag is cleared and the owner has to verify it again in Profile before SMS sign-in works.
- **Bulk import** is covered in [Import and export](/en/features/import-export/): superuser only, create only, with the initial password from `USER_IMPORT_DEFAULT_PASSWORD`.

The department filter on the user list matches **that department only**, not its children.

## Role permission matrix

The role page has the role list on the left and three tabs on the right: **Permissions**, **Data scope** and **Members**.

- **Role code**: starts with an upper-case letter, then upper-case letters, digits and underscores, 2–32 characters, and **cannot be changed after creation** (code refers to roles by code). Code and name must both be unique.
- **Permissions** is a menu tree; buttons sit at the right of their menu's row with an "n/m granted" chip. Two ways of ticking:
  - **Cascade nodes**: ticking a node also ticks all its children and all its ancestors.
  - **Independent nodes**: ticks only that node. If a child is ticked while its parent is not, a warning appears with a one-click fix that adds the parents.
  - The search box matches menu names and permission codes. Changes are a draft until **Save**; **Revert** discards unsaved changes. Editing needs `sys:role:menu:edit`.
- **Data scope** binds data scopes to the role. The role form also has an **Enable data-scope filtering** switch; off means the role sees all data. Writing rules is covered in [Data permissions](/en/features/data-permissions/).
- **Members** only adds or removes "this user has this role"; it does not touch the user. Removing someone's last role shows a warning.

Deleting a role is logical; once deleted it no longer grants anything to anyone.

## Applying permission changes

No. When a role's permissions, data scopes or members change, the affected users' permission cache is cleared after the transaction commits, and **from their next request** the backend uses the new permissions. The permission codes and sidebar cached in their browser are not refreshed automatically (there is no push), so they need to **reload the page** to see new menus and buttons. The E2E suite checks this: after a data scope is unbound, the target account sees the change on reload without signing in again. See also [Data permissions](/en/features/data-permissions/#applying-permission-changes).

## Department rules

- **Department codes** are unique and cannot change after creation; **names** only need to be unique among siblings.
- The **leader** must be an enabled user (checked only when the leader changes).
- A department cannot be moved under itself or one of its descendants.
- A department that **still has users or child departments cannot be deleted**; with children, the delete button is disabled.
- After a department is **disabled**, requests from users who belong directly to it are refused ("The department of this account is disabled"); their sessions are not ended.
- The department tree is limited by data scope: people see only the departments in their scope.
- One xlsx can build a whole department tree; see [Import and export](/en/features/import-export/#importing-a-department-tree).

## Menu types

| Type | In the sidebar | Required |
|---|---|---|
| **Directory** | An expandable group; becomes a plain link when it has no visible children, and is hidden if its path is also invalid | Path |
| **Menu** | A page; the path must be a real frontend route, otherwise it is not shown (with a console warning) | Path |
| **Button** | Not shown; carries permission codes, several per row separated by commas | Permission code |
| **Embedded page** | Opens an external address in an iframe inside a tab (route `/embedded/<name>`); only http / https are loaded, and the page also shows the address and an "open in new tab" button | Address |
| **External link** | Opens in a new browser tab | Address |

In the web app, embedded URLs accept complete HTTP(S) URLs and same-origin root-relative paths such as `/help`. The desktop client requires a complete HTTP(S) URL; opening a relative menu displays instructions to update the URL or use the web app. External links always require complete HTTP(S) URLs.

When upgrading, check existing embedded URLs: relative values without a leading `/`, such as `help`, `./x`, and `docs/a`, no longer load and are rejected on save. Confirm the intended destination before changing them to root-relative paths such as `/help`, `/x`, and `/docs/a`, or to complete HTTP(S) URLs.

- The menu form's **path** can only be picked from existing frontend routes; the **name** must be English letters and digits, starting with a letter.
- A **hidden** menu (not shown in the sidebar) still opens by URL; Profile is one.
- **Disabling a directory disables its whole branch**: it disappears from the sidebar and its permission codes stop counting; re-enabling brings it back. Superusers only lose the sidebar entry; pages without a permission guard still open by URL.
- The menu page flags **dead links** (an "N dead links" badge, with a filter for them): menus whose path has no frontend route. Buttons, external links and embedded pages never count; a directory with at least one visible child does not count.
- Menu titles: the Chinese UI shows the title from the database; other languages look up a built-in translation by path (`menu:<path>`), so renaming a menu's Chinese title does not change the English UI. The form says so.
- A menu cannot be moved under its own descendant, and cannot be deleted while it has children.

## Settings

Almost everything on these four screens is configured in the UI. Related settings:

| Key | Where | Default | Notes |
|---|---|---|---|
| `USER_LOCK_THRESHOLD` · `USER_LOCK_SECONDS` | Config → **Passwords & lockout** | `5` · `300` | Wrong passwords before lockout and for how long; see [Security configuration](/en/reference/security-config/#settings-in-the-ui) |
| `USER_IMPORT_DEFAULT_PASSWORD` | `.env` | empty | Initial password for imported users; empty = user import is off |
| `RBAC_ROLE_MENU_MODE` | `.env` | `true` | Permission-code mode; `false` is casbin mode, see [Data permissions](/en/features/data-permissions/#settings) |
| `RBAC_ROLE_MENU_EXCLUDE` | `.env` | `[]` | Permission codes listed here skip the check |

## Troubleshooting

### New account can't save anything

Symptom: `This account is not allowed to perform admin operations, please contact the administrator`

Cause: the user's **Admin sign-in** is off — the default for created and imported users. With it off they can sign in and read, but every create, update and delete is refused.

Fix: a superuser turns **Admin sign-in** on under **Permissions & security** on the user's row.

### No menu assigned

Symptom: `No menu assigned to this account, please contact the administrator`

Cause: none of their roles ticks a menu — or all their roles are disabled (`The role assigned to this account is disabled, please contact the administrator`).

Fix: tick menus on the role in Roles, or enable the role, or assign another.

### Menu ticked, page refused

Symptom: clicking the menu lands on *Access denied*.

Cause: the menu is ticked but its "query" button isn't. Page guards check the page's query code (see [above](#ui-entry-points)); the menu itself carries no code.

Fix: tick "query" under that menu in the role's Permissions.

### Menu gone from the sidebar

Check in order: the menu or **any parent folder** is disabled (disabling a folder takes its whole branch); the menu is set to hidden; its path has no matching frontend route (Menus flags it as a dead link); their roles don't tick it.

### A whole department locked out

Symptom: `The department of this account is disabled, please contact the administrator`

Cause: the department was disabled. Only people **directly** in it are affected; sub-departments are not.

Fix: re-enable it under Departments.

### Department can't be deleted

Symptom: `This department has users and cannot be deleted` or `This department has sub-departments and cannot be deleted`

Fix: move its people elsewhere and delete or move its sub-departments first.

## Known issues

- Users created by hand or by import start without Admin sign-in and cannot save anything after their first sign-in; the switch's UI description does not match its behaviour, see [above](#superuser-and-admin-sign-in).
- The user delete dialog says it cannot be undone; deletion is actually logical, there is just no restore.
- Data scopes have no "my department and all below" template; see [Data permissions](/en/features/data-permissions/#limitations).
