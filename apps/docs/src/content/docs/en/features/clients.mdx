The repo ships two clients alongside the browser. `apps/desktop` runs the same web build inside Electron and adds what a browser can't do: silent printing, local hardware through native helper processes, a refresh token held by the main process, and auto-update. Each GitHub Release carries installers for Windows, macOS and Linux. `apps/mobile` is a native Expo / React Native app with its own screens, not a WebView around the web pages. It shares the API client and translations with the web app.

This page first installs the desktop app and the phone app and points them at your own backend, then shows how the desktop app updates itself, then each client's capabilities, limits and common problems.

## Quick start

**Desktop**, about three minutes:

1. Download your platform's installer from [GitHub Releases](https://github.com/yile2020/fastapi-react-admin/releases) (see the table below) and install it. It's unsigned, so the OS blocks it once — see [Troubleshooting](#windows-blocks-the-installer).
2. On first launch, enter the backend address on the sign-in page (such as `https://admin.example.com`), then sign in as usual.
3. To switch environments later, click *Change server* on the sign-in page.

**Phone app** (Android only), about three minutes:

1. Download `admin-mobile-<version>.apk` from the same release and open it on the phone to install.
2. Set the server address on the sign-in screen and tap *Test and save*: it probes the address and only saves if it can connect.
3. Sign in with a password or an SMS code.

## Desktop downloads

From [GitHub Releases](https://github.com/yile2020/fastapi-react-admin/releases). Each release has:

| Platform | File | Notes |
|---|---|---|
| Windows 10/11 x64 | `admin-desktop-<version>-setup.exe` | NSIS installer, per-user install into `%LOCALAPPDATA%\Programs`, no admin rights |
| macOS Apple Silicon / Intel | `admin-desktop-<version>-arm64.dmg` / `-x64.dmg` | the matching `.zip` files are for the updater |
| Linux x64 | `admin-desktop-<version>-x86_64.AppImage` | `chmod +x` and run |

The `.blockmap` and `latest*.yml` files are for the updater; you don't download them yourself.

:::caution[The installers are not code-signed]
Windows SmartScreen warns once (*More info → Run anyway*). macOS Gatekeeper says the app "is damaged": right-click → *Open*, or run `xattr -dr com.apple.quarantine "/Applications/Admin Desktop.app"`. The release workflow already passes `CSC_LINK`, `CSC_KEY_PASSWORD` and the `APPLE_*` secrets to electron-builder, so signing (and notarization on macOS) can be turned on by adding those secrets instead of editing the workflow. That path hasn't been exercised with real certificates yet.
:::

## Desktop shell

The shell (Electron 42) contains no business code; the pages are the same `apps/web` build. The renderer talks to the main process through `window.desktop`, which exposes six namespaces (`app`, `config`, `auth`, `print`, `devices`, `updater`). The IPC contract lives in `packages/platform/src/desktop/contract.ts`.

- **Silent printing.** `print.html()` renders HTML in a hidden window and calls `webContents.print({ silent: true })`, so no dialog appears. It uses the printer named in config or the system default. This works for HTML only, not for an existing PDF, so labels are built as HTML with CSS `@page`; `buildLabelHtml()` helps with that. `print.htmlToPdf()` runs the same pipeline to a PDF for checking layouts without a printer. A failed print returns `{ ok: false, reason }`, never a false success. Silent printing is the reason recorded in [`apps/desktop/README.md`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/desktop/README.md) for choosing Electron.
- **Local hardware.** Device adapters start a native helper process and stream its events to `devices.on()`. The shell ships an ID-card-reader adapter. When the vendor's helper `.exe` isn't in `resources/`, the adapter runs in stub mode and `devices.simulate()` fires fake events, so the read → fetch → print flow can be developed on macOS.
- **Credentials.** The renderer is served from `app://local`, so the browser's refresh cookie (`SameSite=Lax`) isn't sent to the backend. The main process therefore keeps the refresh token, encrypted with Electron `safeStorage` (DPAPI on Windows, Keychain on macOS), and hands only the access token to the page. This path has passed type checks but not yet an end-to-end test in a packaged build.
- **Runtime config.** `config.json` in the app's user-data directory holds `serverUrl`, `printerName`, `kiosk`, `autoLaunch` and `updateUrl`. One installer can serve every environment; nothing is compiled in.

```ts
import { isDesktop, desktop } from "@admin/platform/desktop"

if (isDesktop()) {
  const res = await desktop().print.html(html, { pageSize: { width: 60000, height: 40000 } }) // microns
  if (!res.ok) showError(res.reason)
}
```

Measured while building the shell: `print()` takes `pageSize` in microns, while `printToPDF()` takes inches. With `preferCSSPageSize` and an `@page` rule, a 60 × 40 mm label came out at 59.944 × 39.878 mm (0.09% off).

## Auto-update

It uses `electron-updater`. The feed is `updateUrl` from `config.json` if set (a "generic" source: any static HTTP directory, e.g. on a customer's intranet). Otherwise it is the `app-update.yml` baked in at build time, which points at this repo's GitHub Releases. Updates download automatically and install when the app quits. `quitAndInstall(true, true)` installs silently and relaunches; without those flags the NSIS wizard opens and waits for a click. The renderer drives it through `desktop().updater.check()`, `.on()` and `.quitAndInstall()`. Packaged Windows and Linux builds check on their own from the main process (30 s after start, then every 4 hours; set `autoUpdate: false` to turn it off). The unsigned macOS build doesn't check automatically.

| Platform | Auto-update |
|---|---|
| Windows (NSIS) | works; per-user install, so updates need no UAC prompt |
| Linux (AppImage) | works |
| macOS | **does not work** while builds are unsigned: electron-updater checks the running app's code signature |

For an intranet mirror, publish `<version>.exe`, its `.blockmap` and `latest.yml`, uploading `latest.yml` **last** and serving it without caching. The `.blockmap` enables differential downloads, but the first update usually falls back to a full download.

## Building installers

Pushing a `v*` tag runs [`.github/workflows/release.yml`](https://github.com/yile2020/fastapi-react-admin/blob/main/.github/workflows/release.yml). A `prepare` job checks that the tag matches both `apps/web/package.json` and the backend's `__version__`, then creates **one** draft release. A matrix then builds on `windows-latest`, `macos-latest` and `ubuntu-latest`, each platform on its own OS. electron-builder runs with `--publish never` and `gh release upload` attaches the files, because electron-builder's own publisher once raced into two drafts. A person tests the draft before publishing it.

Locally: `pnpm --filter web build`, then `pnpm --filter @admin/desktop package`. The desktop build does not rebuild the web app, so skipping the first step packages a stale UI without any error. For development, run the web dev server on :8888 and then `pnpm desktop:dev`.

## Mobile app

`apps/mobile` uses Expo SDK 57, React Native 0.86 and Expo Router, styled with uniwind (Tailwind CSS v4 for React Native) and `react-native-reusables` components. It targets Android and iOS only.

- **Native screens, not a WebView.** Tabs for Home, Apps and Me, plus notifications, profile and password, settings, a users list → detail → delete flow written as the pattern to copy, and notice detail with attachments. Lists use `FlatList` with infinite queries. Notice bodies (HTML from the web's Tiptap editor) are turned into native components through an allow-list, not rendered in a WebView.
- **Shared with web:** `@admin/api` (envelope handling, single-flight 401 refresh, request types inferred from the generated `schema.d.ts`) and `@admin/i18n`. It does not depend on `@admin/platform`, which is web-shaped.
- **Sign-in:** password or SMS code, both behind the image captcha; accounts with two-factor enter their code as a second step (someone required to enrol but not yet enrolled must do it on the web first). The access token is stored in `expo-secure-store` (Keystore / Keychain), never `AsyncStorage`. The refresh token stays in the httpOnly cookie; on Android, React Native's cookie jar sends it back automatically and keeps it across cold starts.
- **Server address is set in the app** and stored on the device. Before saving, the app probes `/auth/captcha` to confirm the address is a reachable backend. The same `oklch()` colour tokens as the web app render pixel-identical on Android.

## Mobile updates

When a `v*` tag is pushed, the release pipeline uploads the Android installer `admin-mobile-<version>.apk` and an update manifest, `latest-android.json`, to the same GitHub Release as the desktop installers.

- **In-app update check**: release builds on Android check once at startup and prompt when a newer version exists. "Download" opens the APK in the browser; open it when it finishes to install over the current app, keeping sign-in and settings. Settings → About has a "Check for updates" row for checking by hand; a failed check shows "Check failed, tap to retry", never "Up to date".
- **Version from the tag**: written into `app.json` at build time, with `versionCode` derived from it so it always increases.
- **Release signing**: tag builds re-sign the APK with the certificate in the repository secrets and fail if it is missing, so an APK signed with the public debug key is never published. Generate the certificate once and back it up: without it you can't ship an update that installs over the existing app. See [`apps/mobile/scripts/AGENTS.md`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/mobile/scripts/AGENTS.md).
- **Self-hosting**: if GitHub is slow to reach (for example in mainland China) or you deploy on an internal network, put the APK and `latest-android.json` from the Release in one directory on your own server and point the repository variable `MOBILE_UPDATE_MANIFEST_URL` at that manifest when building. The manifest holds the APK's file name, which the app resolves next to the manifest.

Not supported yet: downloading and installing from inside the app, and over-the-air updates of the JavaScript bundle (`expo-updates` needs a dedicated update server).

## Mobile limitations

- Verified by hand on Android only (sign-in → permission gating → paging → detail → delete confirmation → toast). Newer screens, such as SMS sign-in and notice attachments, have so far passed only `tsc`, ESLint and the bundle build. **iOS has never been run.**
- There are no automated mobile tests. The CI gate is `pnpm build`, which includes `expo export --platform android` and catches bundle-time failures only.
- No real-time updates (no socket.io; screens refresh on open and pull-to-refresh). System push, QR scanning and silent printing are out of scope.
- Android only. iOS can't be distributed outside the App Store without a developer account, so there is no iOS build and the app doesn't check for updates there.
- No release tag with an APK has been cut yet: the release pipeline is in place, but the signing certificate has to be added to the repository secrets first (see the previous section).
- Changing the email address needs an email verification code, which only the web has; in the app the email is read-only. A phone number can be bound in the app's profile with an SMS code.

To run it: `pnpm --filter api dev:host` (backend on `0.0.0.0:8088`), then `pnpm mobile:dev`, and open the printed `exp://…:8800` address in Expo Go for SDK 57.

## Troubleshooting

### Windows blocks the installer

The installer isn't code-signed, so SmartScreen blocks it once: click *More info → Run anyway*.

### macOS says it's damaged

Also because it's unsigned. Right-click the app → *Open*, or run `xattr -dr com.apple.quarantine "/Applications/Admin Desktop.app"`. The macOS build doesn't auto-update either; download new versions by hand.

### Desktop never updates

Check in order: is it macOS (no auto-update)? Is `autoUpdate` turned off in `config.json`? In the intranet directory `updateUrl` points to, is `latest.yml` cached, or wasn't it uploaded last? Manual checks ignore `autoUpdate`.

### Desktop build shows old UI

When packaging by hand you skipped `pnpm --filter web build`: the desktop build doesn't rebuild the frontend, so it packages the previous UI without any error.

### App can't reach the server

Messages after *Test and save*:

| Message | Check first |
|---|---|
| `No response within 10 seconds` | Phone and backend on the same network; for local development start the backend with `pnpm --filter api dev:host` to bind `0.0.0.0` |
| `Server returned HTTP 502` and similar | Right address, but the backend isn't running or the proxy is misconfigured |
| `That address doesn't look like this project's backend` | You entered the web frontend or another service |
| `Can't reach that address` | Production needs a **domain + HTTPS**: certificates are issued to domains, so an IP fails TLS |

### Email locked in the app

Changing email needs an email verification code, which only the web app offers so far. Phone numbers can be bound in the app's profile with an SMS code.

## Settings

| Client | Where | Key | Default | Notes |
|---|---|---|---|---|
| Web | Build-time environment variable | `VITE_API_BASE` | `http://127.0.0.1:8088` | Backend address, baked into the frontend build |
| Desktop | `config.json` in the app data directory, read at run time | `serverUrl` | empty | Backend address; one installer can serve different environments. Entered on the sign-in page at first launch; change it later via "Change server" on the same page |
| Desktop | same | `printerName` | empty | Printer for silent printing; empty = system default |
| Desktop | same | `kiosk` | `false` | Full-screen kiosk mode |
| Desktop | same | `autoLaunch` | `false` | Start at login (packaged builds only) |
| Desktop | same | `updateUrl` | empty | Auto-update feed; empty = GitHub Releases |
| Desktop | same | `autoUpdate` | `true` | Scheduled update checks from the main process (Windows / Linux: 30 s after start, then every 4 h); `false` turns them off, manual checks still work |
| Mobile | The server address setting in the app, stored on the device | — | Build-time `EXPO_PUBLIC_API_BASE`, or `http://127.0.0.1:8088` if unset | Probes `/auth/captcha` before saving to confirm it is reachable. `EXPO_PUBLIC_*` is replaced at build time, so after packaging the address can only be changed in the app |
