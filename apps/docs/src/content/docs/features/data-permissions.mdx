权限分两道，互不替代：**功能权限**决定一个人能打开哪些页面、看到哪些按钮、调哪些接口；**数据范围**决定接口返回哪些行 —— 同样能打开用户管理，部门经理只看到本部门的人，总部看到全部。数据范围在后端查询时自动套上，业务代码不用为它写一行判断。

本页先用种子数据走一遍「只看本部门」，再讲一次请求按什么顺序判定、规则怎么写，最后是常见问题和开发者要注意的写法。

## 界面入口

| 入口 | 路径 | 权限码 | 做什么 |
|---|---|---|---|
| **系统管理 → 数据权限** | `/system/data-permission` | 范围：`data:scope:list` · `add` · `edit` · `del`，改范围里挂哪些规则 `data:scope:rule:edit`；规则：`data:rule:list` · `add` · `edit` · `del` | 左栏是数据范围，右栏是这个范围里的规则 |
| **系统管理 → 角色管理 →「数据范围」** | `/system/role` | 查看 `sys:role:list`，修改 `sys:role:scope:edit` | 给角色绑定数据范围；角色表单里还有一个「启用数据权限过滤」开关，关掉 = 这个角色不受数据范围限制（如集团总部角色） |

⚠️ 打开「数据权限」这一页，前端路由守卫目前认的是 `data:scope:add`，不是 `data:scope:list` —— 只授了「查询」的角色打不开这一页。

## 上手步骤

用种子里的「财务专员」角色（绑的是「本部门数据权限」）和它下面的用户王芳走一遍，大约 5 分钟：

1. 用管理员登录，打开 **系统管理 → 角色管理**，选中「财务专员」。在「数据范围」页签能看到它绑了「本部门数据权限」，角色表单里的「启用数据权限过滤」是开着的。
2. 切到「功能权限」页签，勾上 **系统管理 → 用户管理** 和它下面的「查询」，保存。这一步给的是功能权限：没有它，王芳连用户管理都打不开。
3. 另开一个无痕窗口，用 `wangfang` / `123456` 登录，打开 **系统管理 → 用户管理**：列表里只有「财务人事中心」的人。
4. 回到管理员窗口，在 **系统管理 → 数据权限** 里把「本部门数据权限」换成别的规则或解绑，王芳那边刷新页面就变 —— 不用重新登录。

## 处理顺序

每次请求按下面的顺序判定，前两步看「能不能调这个接口」，后三步看「能看到哪些行」：

<DiagramFlow {...flows.dataScope.zh} />

- **多个角色取最宽**：只要有一个启用的角色关了「启用数据权限过滤」，别的角色配的限制一条都不看。给人加角色既是加能力，也可能是减限制。
- **规则只对有那一列的表生效**：「部门 ID 等于当前用户部门」落在用户表上是 `dept_id = 你的部门`；部门表没有 `dept_id` 列，这条规则对部门列表不起作用，部门列表照样全显示。
- **OR 会抬掉 AND**：所有规则先拍平，再组合成「（全部 AND）或（任一 OR）」。同一个范围里混用两种，数据权限页会挂一条告警。

## RBAC 与数据范围

| | RBAC（权限码） | 数据范围（行级） |
|---|---|---|
| 回答的问题 | 这个人能不能调 `GET /sys/users`？ | 调了之后能看到哪些用户？ |
| 在哪配 | **系统管理 → 菜单管理**（按钮上的权限码）+ **系统管理 → 角色管理 → 功能权限** | **系统管理 → 数据权限** + **系统管理 → 角色管理 → 数据范围** |
| 在哪拦 | [`rbac.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/common/security/rbac.py) 的 `rbac_verify`，按接口 | [`data_scope.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/common/security/data_scope.py) 的 `DataScopedCRUD`，按 DAO |
| 被拒的表现 | HTTP 403 | 行变少（详情接口是 404） |

## RBAC 判定

菜单在 `sys_menu` 里（type 0 目录、1 菜单、2 按钮），按钮行的 `perms` 字段放逗号分隔的权限码，角色绑定菜单。接口自己声明要哪个码：

```python
@router.get(
    '/{pk}',
    summary='获取用户信息',
    dependencies=[Depends(RequestPermission('sys:user:list')), DependsRBAC],
)
```

`rbac_verify` 按顺序判：超管直接放行；用户至少要有一个启用的角色，角色至少挂了一个菜单；`GET` / `OPTIONS` 以外的请求还要求 `is_staff`（后台管理操作权限）；最后，接口的权限码必须出现在某个启用角色、某个启用菜单的 `perms` 里。菜单「启用」指的是**它和每一级上级**都启用 —— 停用一个目录，下面按钮的权限码一起失效。

前端登录后从 `/auth/codes` 拉一次权限码：[`<Can perm="…">`](https://github.com/yile2020/fastapi-react-admin/blob/main/packages/platform/src/auth/can.tsx) 控制按钮显隐，路由 `beforeLoad` 里的 `requirePerm()` 无权限时跳 `/403`。这两处都只管显示，真正的边界在后端。

:::caution
没有声明权限码的路由，`rbac_verify` 直接放行（提前 return）。读接口也必须挂权限码：issue #30 之前，`/sys/users`、`/logs/opera` 等几个 `GET` 接口只校验了登录，一个只绑了「仪表盘」的账号就能拿到全量用户列表。
:::

## 从规则到 SQL

链路是 **角色 → 数据范围（`sys_data_scope`）→ 数据规则（`sys_data_rule`）→ 一个条件**。数据范围只是一捆规则的名字；规则有五个字段，拿种子数据里的一条举例：

| 字段 | 值 | 含义 |
|---|---|---|
| 模型 | `__ALL__` | 所有带这一列的模型；也可以写具体模型名，如 `Dept`、`User` |
| 字段 | `__dept_id__` | 字段模板，解析成 `dept_id`；另一个字段模板是 `__created_by__` |
| 运算符 | `AND` | `AND` 或 `OR`，见下一节 |
| 表达式 | `==` | 另有 `!=`、`>`、`>=`、`<`、`<=`、`in`、`not in` |
| 值 | `${dept_id}` | 当前用户的部门；另有 `${user_id}`、`${now}` |

落到 `User` 模型上就是 `sys_user.dept_id = <当前用户的 dept_id>`。`Dept` 上没有 `dept_id` 这一列，所以同一条规则对部门列表不起作用。

[`filter_data_permission_for_user()`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/common/security/permission.py) 的求值顺序：

1. 超管 → 不过滤。
2. 只要有一个启用的角色关掉了「启用数据权限过滤」→ 不过滤。
3. 把所有启用角色、所有启用数据范围里的规则收进**同一个集合**。开了过滤却一条规则都没有 → **一行都看不到**。
4. 编译出适用于本次查询模型的条件，再组合：

<details>
<summary>组合条件的源码（开发者）</summary>

```python
where_list = []
if where_and_list:
    where_list.append(and_(*where_and_list))
if where_or_list:
    where_list.append(or_(*where_or_list))
return or_(*where_list) if where_list else or_(1 == 1)
```

</details>

最后那个 `or_(1 == 1)` 只兜「规则都没问题、但没有一条打在这个模型上」的情况 —— 一条打在 `User` 上的规则不会把部门藏起来。

## OR 与 AND 的组合

因为上面的形状是 `or_(and_(全部 AND), or_(全部 OR))`。配了「`parent_id == RA`（AND）」和「`status == 1`（OR）」，结果是并集而不是交集，OR 那条把限制整个抬掉了。规则在这一步之前已经跨数据范围、**跨角色**拍平，所以来自两个不同角色的 AND 规则同样是求交集。数据权限页上，只要一个数据范围里同时有 AND 和 OR 规则，就会挂一条告警。

## 多角色合并

取**最宽**的。只要有一个启用角色关掉了过滤，其它角色配的限制一条都不看 —— 给人加角色是「加能力」，同时也在「减限制」。停用的角色、停用的数据范围不参与。

## 自动过滤

不用。JWT 中间件认证通过后把当前用户放进 `ContextVar`，`DataScopedCRUD` 基类在 `select()`、`select_model()`（按主键取详情）和 `count()` 三处把条件拼上。只覆盖 `select()` 会漏掉详情接口：现在对范围外的部门请求 `GET /sys/depts/{pk}`，返回的是 404，而不是那条数据。

每个 DAO 都必须表态：要么继承默认（过滤），要么显式写 `data_scope_enabled = False` 并注明理由。有一条测试扫描所有 `crud_*.py`，还有类直接继承 `CRUDPlus` 就红；另一条核对豁免清单和代码是否一致。目前受数据范围约束的有：用户、部门、角色、文件、登录 / 操作日志、定时任务及执行记录。豁免的理由都写在 [`test_data_scope_coverage.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/app/admin/tests/security/test_data_scope_coverage.py) 里，例如：菜单（滤掉会让侧边栏空白）、字典与参数配置（表单下拉依赖它们）、规则表和范围表自身（会把管理员自己锁在外面）、公告（表里没有可过滤的归属字段）。

## 后台任务（Celery）

没有请求就没有「当前用户」，没有当前用户就**不过滤** —— 对清理日志、CLI、启动期代码这是对的。但凡是**代替某个人**读写业务数据的代码，必须显式声明身份：

```python
with scoped_to_user(user):
    async with async_db_session() as db:
        stmt = _restrict_ids(await spec.select(filters, user), spec, ids)
        ...
```

这段来自导出的 worker（[`export_service.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/app/admin/service/export_service.py)）：不这么写的话，一个只能看本部门的人发起的大批量导出，在 worker 里会查回全表，而且不报错。`scoped_to_user(None)` 会故意抛 `ValueError`。[AI 助手](/features/ai-assistant/)的每一次工具调用也走同一个 `scoped_to_user`。反方向的 `bypass_data_scope()` 只给请求里「不展示给用户」的系统内部读用，比如登录时查用户、新建时的唯一性检查。

## 配错防护

两道防线：

- **保存时校验**（[`data_rule_service.py`](https://github.com/yile2020/fastapi-react-admin/blob/main/apps/api/backend/app/admin/service/data_rule_service.py)）：模型或字段不存在、用了被排除的字段（`id`、`sort`、`deleted`、`deleted_time`、`created_time`、`updated_time`）、值转不成列的类型（给 bigint 列配 `abc`）、`__ALL__` 配裸字段名 —— 直接拒绝并说明原因。
- **运行时 fail-closed**：只要有一条规则读不懂，整个过滤器收紧成 `false()`，一行都看不到。模板变量取不到值（没有部门的用户遇到 `${dept_id}`）时，这条规则匹配不到任何行，而不是把字面量 `'${dept_id}'` 拼进 SQL（在 SQL Server 上那会直接 500）。

早期版本遇到落不到列上的规则是直接跳过的。种子里的「本部门数据权限」当时配的是 `Dept.__dept_id__`，而 `sys_dept` 没有 `dept_id` 这一列 —— 名字叫「本部门」，实际效果是全部部门可见，界面上没有任何提示。

## 权限生效

不用。用户的权限快照（Redis 键 `fba:user:<id>`）会在角色、数据范围、规则变更时被清掉，下一个请求重新生成。后端测试和浏览器端到端测试都验证了「不重新登录就生效」。

## 常见问题

### 配了范围还是看到全部

按顺序排查：

1. 这个人是不是超管 —— 超管永远不过滤。
2. 他的**所有**角色里，有没有哪个关了「启用数据权限过滤」（比如还挂着一个管理员角色）。
3. 规则有没有落在这张表上：规则写的模型是 `Dept`，对用户列表就不起作用；用 `__dept_id__` 这类字段模板时，表里要真有这一列。
4. 同一批规则里有没有 OR 规则，它会把 AND 的限制整个抬掉。

### 一行都看不到

常见原因：

- 角色开了「启用数据权限过滤」，却一个数据范围都没绑 —— 开了过滤又没有规则，按「一行都不给」处理。
- 用户没有部门，而规则用的是 `${dept_id}`：取不到值的规则匹配不到任何行。
- 有一条规则读不懂（比如对应的列被删了）：整个过滤收紧成一行都不给，宁可多拦也不放开。

### 打开页面就是无权访问

现象：页面跳到「无权访问」，或接口返回 403。

原因：缺功能权限，和数据范围无关。到 **角色管理 → 功能权限** 给角色勾上这一页和它的「查询」按钮。

⚠️ **系统管理 → 数据权限** 这一页目前认的是「新增」（`data:scope:add`），只勾「查询」打不开，这是已知问题。

接口直接返回下面这几句的，是账号本身的问题：

| 提示 | 原因 |
|---|---|
| `用户所属角色已被锁定，请联系系统管理员` | 他没有启用的角色（全被停用，或一个都没分配） |
| `用户未分配菜单，请联系系统管理员` | 角色上一个菜单都没勾 |
| `用户已被禁止后台管理操作，请联系系统管理员` | 用户的「后台管理」开关关着：查询照常，新增、修改、删除一律拒绝 |

### 保存规则被拒

规则在保存时就校验，提示会说清哪里不对：

| 提示 | 改法 |
|---|---|
| `所选模型上不存在该字段` | 换一个这张表真有的字段 |
| `模型为「所有模型」时，字段必须使用模板变量` | 「所有模型」只能配 `__dept_id__` / `__created_by__` 这类字段模板 |
| `该字段不允许用于数据过滤` | `id`、`sort`、`deleted`、创建 / 更新时间这几列不能做规则 |
| `值与字段类型不匹配` | 比如给数字列填了文字；部门、用户这类 ID 列填数字或 `${dept_id}` |

### 改权限后生效时机

不用。角色、范围、规则一改，后端就清掉这些人的权限缓存；对方刷新页面，按钮和数据都按新的来。

## 已知限制

- 值模板只有 `${user_id}`、`${dept_id}`、`${now}` 三个，没有「本部门及所有下级部门」这种模板。种子里的「部门及以下数据权限」是用写死总部（HQ）编码和 ID 的两条规则拼出来的。
- `DataScopedCRUD` 只管读。它不改写 `UPDATE` / `DELETE` 语句，所以不先经过受控 DAO 读一遍、直接按 ID 改数据的写路径，不在数据范围的保护之内。
- `exists()` 刻意不过滤：它被用来做唯一性校验，过滤之后用户会因为「看不见」而建出一条重复记录。
- 上级部门被过滤掉时，可见的子部门会被提到树的顶层。
- 超管永远不过滤。开放接口（AK/SK 签名）刻意读全量数据，它的边界靠「每个应用被授权调哪些接口」和「对外 schema 只放哪些字段」来守。

## 配置项

数据范围本身都在界面上配。下面几项是给开发者的，只能在 `.env` / `conf.py` 改，改完重启后端：

| 键 | 默认值 | 说明 |
|---|---|---|
| `DATA_PERMISSION_MODEL_EXCLUDE` | `DataScope` · `DataRule` · 两张关联表 | 哪些模型不参与数据过滤（规则编辑器里选不到） |
| `DATA_PERMISSION_COLUMN_EXCLUDE` | `id` · `sort` · `deleted` · `deleted_time` · `created_time` · `updated_time` | 哪些列不能作为规则的字段 |
| `DATA_PERMISSION_TEMPLATE_VARIABLES` | `${user_id}` · `${dept_id}` · `${now}` | 规则值能用的模板变量 |
| `RBAC_ROLE_MENU_MODE` | `true` | `true` = 权限码模式（角色 → 菜单 → 权限码）；`false` = casbin 模式，按接口路径 + 方法鉴权，依赖权限码的功能在这个模式下一律拒绝 |

## 在线体验

用 `admin` / `123456` 登录[在线演示](https://fra.wubunan.com/sign-in)，打开 **系统管理 → 数据权限**。按种子数据，「部门及以下数据权限」这个范围里一条是 OR、一条是 AND，所以会显示上面说的那条告警。**系统管理 → 角色管理 → 数据范围** 能看到每个角色绑了哪些范围。`admin` 是超管，永远不被过滤；想看过滤效果，新建一个用户、给他一个开了过滤的角色，再用这个用户登录。演示环境是公开的，数据可能被别人改动；请别改种子里的角色和范围，想试就新建一个。
