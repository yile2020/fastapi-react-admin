想知道系统现在好不好，有两种看法：**后台里的监控页**给人看 —— 服务器的 CPU、内存、磁盘，Redis 的内存和每秒操作数，只显示此刻；**健康检查地址** `/api/health/status` 给外部监控系统探 —— 不用登录，一次列出 API、数据库、Redis、调度器和后台任务进程是否正常，全部正常回 200、任一异常回 503。

本页先带你看一次健康检查、故意停掉一个进程看它怎么报，再讲后台任务的心跳是怎么来的，然后是两个监控页和常见问题。

## 界面入口

| 入口 | 路径 | 谁能用 |
|---|---|---|
| **系统监控 → 服务器监控** | `/monitor/server` | 超级管理员 |
| **系统监控 → Redis 监控** | `/monitor/redis` | 超级管理员 |
| **系统监控 → 在线用户** | `/monitor/online` | 超级管理员，见[登录会话](/features/login-sessions/) |
| 工作台「服务状态」卡片 | `/dashboard` | 超级管理员 |
| 健康检查 | `/api/health/status` | 不用登录 |

监控类页面和接口按**超级管理员**判，没有权限码：给普通角色授了这几个菜单也打不开。

## 上手步骤

本地用 `pnpm dev` 起着全部服务时，大约 5 分钟：

1. 浏览器打开 `http://127.0.0.1:8088/api/health/status`：返回 200，`services` 里 `api`、`database`、`redis`、`scheduler`、`worker` 五项都是 `ok`，最后带着版本号和提交号。
2. 在 `pnpm dev` 的终端里停掉 worker 那个进程（或 `docker stop` 生产环境的 worker 容器），等 3 分钟再刷新：`worker` 变成 `stale`，整个响应变成 503。
3. 把 worker 起回来，一分钟内恢复 200。
4. 用超级管理员打开 **系统监控 → Redis 监控**，把刷新改成 5 秒，看每秒操作数的趋势线一点点长出来。

接外部监控（Uptime Kuma、云监控等）时，探这个地址、按状态码判断即可，见[部署到服务器](/getting-started/deployment/#外部监控)。

## 心跳从哪来

数据库和 Redis 是当场 ping 的；调度器和后台任务进程没有端口可探，靠它们自己写心跳：

<DiagramFlow {...flows.health.zh} />

- **180 秒才报异常**：默认等于 3 个周期，重启、发版换容器时漏一两拍不会误报。
- **只列自己运维的组件**：邮件、对象存储、第三方登录、AI 服务商坏了不会让它 503 —— 那些去各自的投递记录、调用日志里看。
- **不泄露细节**：出错时只给异常的类型名，不带异常消息，匿名访问者看不到连接串之类的东西。

## 两个监控页

**服务器监控**：

- 顶部四个指标：CPU、内存、占用最高的那块磁盘、运行时长；CPU 和内存带趋势线
- CPU 核数与频率；内存总量 / 已用 / 空闲
- 系统：主机名、操作系统、架构、IP、分区数
- 后端进程：Python 版本、启动时间、CPU、常驻内存、虚拟内存、解释器路径
- 磁盘列表（`overlay`、`tmpfs` 这类虚拟文件系统不列）

**Redis 监控**：

- 已用内存与上限（`maxmemory`）、内存碎片率（带解读提示）
- 键数量 —— **只是当前库**（`DBSIZE`），同一台 Redis 上其他库的不算
- 每秒操作数和它的趋势
- 客户端：已连接、阻塞中、被拒绝（被拒绝是累计值）
- 版本、模式、角色、端口（容器里看到的端口）
- 命令统计：调用最多的前 10 条，可搜索

**刷新**：手动，或每 5 / 10 / 30 / 60 秒，默认 10 秒，选择写进地址栏（`?refresh=`）。页签切到后台时停止轮询，切回来再继续。

趋势线最多保留 40 个点，关掉页面就没了 —— 这两页是「现在怎么样」，不是监控系统。要看历史曲线、要告警，接 Prometheus / Zabbix / 云监控这类专门的系统。

## 健康检查接口

`GET /api/health/status`，不用登录、不限流、不进操作日志。并发检查五项：

| 项 | 怎么判 |
|---|---|
| `api` | 能响应就是正常 |
| `database` | `SELECT 1`，5 秒超时 |
| `redis` | `PING`，3 秒超时 |
| `scheduler` | beat 的调度循环每一拍写一次心跳（至少每 60 秒一拍，写入最多每 15 秒一次） |
| `worker` | beat 每 60 秒派一个 `health.heartbeat` 任务，worker 执行时写心跳 |

心跳超过 180 秒没更新记 `stale`，从没写过记 `missing`，Redis 读不了或调度器本身不正常时 worker 记 `unknown`（worker 的心跳是 beat 派发的，beat 不在就无从判断）。

**全部正常返回 200，任何一项不正常返回 503**，响应体里逐项列出状态和心跳的秒数。出错时只给异常的类型名，不带异常消息（免得把连接串之类的东西漏给匿名访问者）。后端整个挂了时，nginx 直接返回 503 和 `{"status":"unavailable"}`，并带上 `Retry-After: 15`。

响应体最后还带 `version`（版本号）和 `commit`（7 位提交号），用来确认线上跑的是哪一版；它们不影响 200 / 503 的判定，提交号没有写进镜像时是 `null`。前端那一份在 `/version.json` 里，登录后点顶栏的「帮助 → 关于」可以并排看到前后端的版本，两端不一致会标出来。

外部监控该探哪个地址、为什么不能用 `/healthz`，在[部署到服务器](/getting-started/deployment/#外部监控)里。容器编排用的是另一个只查数据库和 Redis 的 `/health/ready`。

工作台的「服务状态」卡片读的是同一套检查，外加网页 / 桌面 / 移动三端各有多少在线会话；它不自动轮询，20 秒内重复打开用缓存。

## 常见问题

### 健康检查一直是 503

看响应里哪一项不是 `ok`：

| 状态 | 意思 | 先查什么 |
|---|---|---|
| `database` / `redis` 是 `error` | 连不上 | 数据库、Redis 进程和网络；`error` 字段里是异常类型名 |
| `scheduler` 是 `missing` 或 `stale` | beat 没起，或卡住了 | beat 进程 / `fba_beat` 容器的日志 |
| `worker` 是 `stale` | worker 没起，或 3 分钟没处理过心跳任务 | worker 进程的日志；队列是不是被别的项目抢了（见[定时任务](/features/scheduler/#到点了任务没跑)） |
| `worker` 是 `unknown` | 调度器本身不正常，worker 的心跳无从判断 | 先修调度器 |

### 返回 unavailable

现象：503，响应体是 `{"status":"unavailable"}`。

原因：这是 nginx 回的 —— 后端进程整个连不上（没起、崩了、正在重启）。看 api 容器的日志。

### 监控页打不开

服务器监控、Redis 监控按超级管理员判，没有权限码；给角色授了菜单也打不开。

### Redis 键数比实际少

键数量只是**当前库**（`DBSIZE`），同一台 Redis 上其他库的键不算。

### 监控到的是容器

它看的是跑后端 API 的那台机器或容器，不是数据库、Redis 所在的机器；容器里的 CPU 和内存是容器看到的值。

## 配置项

都在 `.env`，改完重启后端：

| 键 | 默认值 | 说明 |
|---|---|---|
| `HEARTBEAT_MAX_AGE_SECONDS` | `180` | 心跳多久没更新就算不正常；默认等于 3 个周期，漏一两拍（重启、发版换容器）不报警 |
| `SCHEDULER_HEARTBEAT_REDIS_KEY` · `WORKER_HEARTBEAT_REDIS_KEY` | `fba:health:scheduler_heartbeat` · `fba:health:worker_heartbeat` | 心跳写在 Redis 的哪个键 |

监控页的刷新间隔在页面上选，不需要配置。

## 已知限制

- 服务器监控看的是**跑后端 API 的那台机器（或容器）**，不是数据库、Redis 所在的机器。IP 是向外发一个 UDP 连接时用的本机地址，取不到就显示 `127.0.0.1`。
- 不存历史、不告警。
- beat 卡住但循环还在转时，调度器心跳仍可能在写，健康检查看不出来。
- 两个监控页没有后端测试和 E2E；健康检查有。
